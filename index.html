01

First, forget the chain.

Most blockchains organize activity around a single, linear sequence of blocks. Retium takes a different architectural approach — using prime-number mathematics and a multi-directional mesh structure so many blocks can exist and process transactions at the same time.

A single chain processes one block at a time, creating a throughput bottleneck. Retium's mesh can contain multiple valid blocks simultaneously, processing transactions in parallel.

02

Retium starts with mathematics.

Every tick, a new prime number enters the network. New block IDs are derived from prime factorization and the mathematical relationships between primes. Because the rules are purely mathematical, the structure is deterministic — anyone can run the same calculation and get the same result.

Don't wait for a block to be created.

Retium keeps multiple blocks open at the same time — typically between 3 and 20 depending on network activity — and routes each transaction directly into an available open block. There is no waiting for a block to fill up.

03

No waiting room.

Traditional

Transaction → Mempool → Wait → Block

Transactions pile into a shared mempool, where they wait — potentially being reordered — until a miner or validator includes them in a block.

Retium

Transaction → Router → Open Block

Retium's architecture does not use a traditional shared mempool. When a transaction arrives, the Router assigns it directly to an open block — no waiting stage in between.

Removing the conventional mempool changes the transaction flow and removes the waiting-pool stage. Transactions are processed in the order they arrive, routed by weight for efficiency.

04

Complexity decides the weight.

Retium uses a weight-based fee model. Every transaction and contract is assigned a computational weight from 1 to 5 — a simple transfer costs less than a complex smart-contract interaction. There are no gas auctions and no bidding wars.

05

Consensus, decided by mathematics.

In Proof of Work, block structure is decided by energy. In Proof of Stake, it is influenced by token ownership. In Proof of Math (PoM), mathematics determines which block structures can exist — validators execute what the math dictates, rather than choosing it.

06

Specialized validators, working together.

Retium distributes network responsibility across three distinct validator roles. Each handles one part of the journey from transaction to finality.

W
Transaction Validation

Worker

Workers validate individual transactions. They independently check that each transaction is legitimate, correctly formed, and safe to execute. The Matchmaker assigns five Workers to each transaction; at least three must approve it. It is the most accessible role — designed to run light, potentially on phones and laptops.

Click or tap to learn more
K
Network Coordination / Block Planning

Keeper

Keepers plan blocks, coordinate the network, store full mesh state, and manage tick advancement. After a block is sealed, the Keeper layer checks it through deterministic consensus — Keepers independently recompute the same mathematical result from the same inputs.

Click or tap to learn more
S
Block Finality

Suit

Suits coordinate block finality. Five independent Suits are assigned to each sealed block and coordinate finality by watching for Keeper agreement. Once required consensus is reached, a Suit broadcasts the finality verdict and the block becomes HardFinal.

07

Confirmation and finality are not the same thing.

Retium separates a transaction's own confirmation from the finality of the block that contains it. This lets a transaction confirm quickly while the block continues through its own lifecycle.

Block lifecycle

Block finality is handled later by Suits, allowing a user's transaction to confirm quickly while the block moves through its own planned, open, sealed, final lifecycle.

08

Write the logic. Compile to WASM.

Retium smart contracts execute as WebAssembly (WASM). Rust is the recommended native language, and any language that compiles to WASM can be used — including C, C++, AssemblyScript, Go (TinyGo) and Zig. The source language is compiled before execution.

Rust / C / C++ Go / Zig / AS → Compile → WASM → Retium Runtime → Execution

RCP-1

Retium Contract Protocol

RCP-1 provides a unified contract standard for tokens, NFTs, governance, game logic and other applications. Every contract declares its role through embedded metadata, so contracts are self-describing — with deterministic routing, pricing, and evolution.

// Every Retium contract implements the RetiumContract trait
// RCP_METADATA is embedded in the compiled WASM binary

const RCP_METADATA: &[u8] = b"RCP_METADATA";

fn handle_transfer(caller: &str, args: &[String]) -> String {
  let to = &args[0];
  let amount = parse_u128(&args[1]);
  let from_balance = get_balance(caller);
  if from_balance < amount {
    return "{\"error\":\"insufficient balance\"}".into();
  }
  set_balance(caller, from_balance - amount);
  set_balance(to, get_balance(to) + amount);
  "true".into()
}

09

Not a fork. A new foundation.

Retium is a multi-dimensional Layer-1 built from the ground up on its own architecture. It was written entirely from scratch in Rust — no forks, no borrowed consensus, no inherited limitations.
